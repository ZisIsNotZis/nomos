# 挂宽 LoRA：24 层全覆盖，验证 PPL 6.03 → 6.09，选窄版做后续测量

## 结论

同一份数据（288 训练 / 78 验证）、同一套超参（r=16 alpha=32、3 epoch、54 步、lr 1e-4、有效 batch 16、种子 0）下，把 LoRA 从 6 个全注意力层的 q/k/v/o + MLP 扩到还包括 18 个线性注意力层的 `in_proj_qkv / in_proj_z / in_proj_a / in_proj_b / out_proj`（186 个模块、16.82M 可训练参数）：

| | 窄版（6 全注意力层 + MLP） | 宽版（18 线性层 + 6 全注意力层 + MLP） |
| --- | --- | --- |
| 训练 loss / PPL | 1.4376 / 4.2105 | **1.4174 / 4.1262**（更低 0.0202） |
| 验证 loss / PPL | **1.7972 / 6.0325** | 1.8070 / 6.0923（更差 0.0099 / 0.06 PPL） |
| 验证 − 训练 | 0.3596 | 0.3897（差距拉大 0.0301） |
| LoRA 模块 / 张量 | 84 / 192 | 186 / 372 |
| 可训练参数（占比） | 10 911 744（0.794%） | 16 819 200（1.219%） |
| 适配器字节 | 43 675 104 | 67 332 688 |
| 峰值显存（分配 / 保留） | 8.74 / 9.98 GiB | 6.43 / 6.98 GiB |
| 耗时（进程内计时，含全部评测） | 828.6 秒 | 1312.2 秒 |

**扩宽没有换来更好的泛化**：训练 loss 更低、验证 loss 更高、两者差距从 0.360 涨到 0.390，而且宽版验证 loss 在第 2 epoch 见底（1.8058）后第 3 epoch 回升到 1.8070，窄版则仍在下降（1.8032 → 1.7972）。**后续测量用窄版** `.tmp/sft/adapter-narrow/`，理由见最后一节。

两版数字全部由脚本落在 `evidence/sft/log.jsonl`（窄）与 `evidence/sft/log-wide.jsonl`（宽），本文件只引用那些记录，不重算。

## 覆盖：打印出来的 186 个模块，不是推测

`report_lora_coverage()` 在挂完 LoRA 之后遍历 `named_modules()`，只统计真的带 `lora_A` 的模块，按名字后缀计数，期望值从模型自己的 `config.text_config.layer_types` 推出（18 个 `linear_attention` + 6 个 `full_attention`），对不上就断言失败。`lora_coverage` 记录：

```
modules_per_name: down_proj 24, gate_proj 24, up_proj 24,
                  in_proj_qkv 18, in_proj_z 18, in_proj_a 18, in_proj_b 18, out_proj 18,
                  q_proj 6, k_proj 6, v_proj 6, o_proj 6
modules_total: 186   lora_tensors: 372
projections_by_owner: linear_attn 90, self_attn 24, mlp 72
```

186 = 18 层 × 5 个线性注意力投影 + 6 层 × 4 个全注意力投影 + 24 层 × 3 个 MLP 投影，**24 层每层都有 delta**。命中的完整名字例如 `model.language_model.layers.22.linear_attn.in_proj_qkv`。断言同时排除了误伤：视觉塔的 `proj`、`qkv`、`linear_fc1/2` 不以这些后缀结尾，没有被匹配进来。

第一次 backward 后的梯度检查：372 个可训练张量里 186 个有非零梯度（`gradient_check`，正好是 186 个 `lora_B`；`lora_A` 第一步必然零梯度），16 819 200 个参数里非零元素 9 151 264 个。窄版同一条记录是 192 张量 / 96 个。

## 两版逐 epoch 对照

| epoch | 窄版训练 | 窄版验证 | 窄版差 | 宽版训练 | 宽版验证 | 宽版差 |
| --- | --- | --- | --- | --- | --- | --- |
| 0（训练前） | — | 2.4285 / 11.34 | — | — | 2.4277 / 11.33 | — |
| 1 | 1.7593 | 1.8650 / 6.456 | 0.1057 | 1.7432 | 1.8640 / 6.449 | 0.1208 |
| 2 | 1.5247 | 1.8032 / 6.069 | 0.2785 | 1.5065 | 1.8058 / 6.085 | 0.2993 |
| 3 | 1.4376 | 1.7972 / **6.033** | 0.3596 | 1.4174 | 1.8070 / 6.092 | 0.3897 |

训练 loss 宽版每个 epoch 都更低（-0.016 / -0.018 / -0.020），验证 loss 只有第 1 epoch 低 0.001，之后两个 epoch 都更高（+0.0026 / +0.0099）。逐 step loss 两版几乎重合（第 1 步 2.3681 vs 2.3693，第 46 步最低 1.2630 vs 1.2654，第 54 步 1.5784 vs 1.5862），所以差别不在学习率或顺序，在容量。

## 过拟合：是，差距被拉大

三条证据一致：

1. 验证减训练的差在三个 epoch 上都更大：0.1208 / 0.2993 / 0.3897 对 0.1057 / 0.2785 / 0.3596，到第三 epoch 多出 0.0301。
2. 宽版验证 loss 出现拐头（第 2 epoch 1.8058 → 第 3 epoch 1.8070），窄版没有。多出来的容量在第 3 epoch 买的全部是训练集上的拟合。
3. 宽版的可训练参数多了 54%（10.9M → 16.8M），训练样本只有 288 条、39 个会话，验证集 78 条、12 个会话。

量级上要诚实：验证 PPL 的绝对差是 6.0325 → 6.0923，相对 1.0%；两版评测的 batching 造成的同源差（见下一节）是 11.3418 → 11.3329，相对 0.08%。也就是说宽版第三 epoch 的落后是评测噪声的十余倍，可以判定，但**不能**据此说扩宽有害——只能说在这 288 条数据上扩宽没有带来泛化收益，并且提前开始记忆。

## 与窄版唯一没保持一致的：micro-batch

窄版 2 × 8 梯度累积，宽版 1 × 16 —— 有效 batch 仍是 16，每步的 16 条样本与顺序完全相同，种子、步数、lr、warmup、alpha、r 都相同。原因不是选择而是显存：窄版开跑时卡上剩 13.5 GiB，这次 `torch.cuda.mem_get_info` 只报 7.3 GiB（同一个 llama-server 占 12.9 GiB，另一个 python 进程占 2.6 GiB，都不是本仓库的）。窄版在 micro-batch 2 下峰值分配 8.74 GiB，按 7.3 GiB 跑必然 OOM，所以降到 1 并把累积翻倍以守住有效 batch。

这条偏差带进来的只有反向累加的浮点分组顺序不同，证据就是两版训练前验证 loss 的差：2.428494 对 2.427708（0.0008）。它是本对比的噪声下限，上面对差的判断都按这个下限来读。

显存反而因此更低（6.43 GiB 分配 / 6.98 GiB 保留，对窄版 8.74 / 9.98），耗时因此更长（1312.2 秒对 828.6 秒，+58%）：micro-batch 1 的 kernel 启动次数翻倍，加上多出来的 5.9M 可训练参数的反向。

## 选窄版做后续测量的对象

选 `.tmp/sft/adapter-narrow/`（sha256 `5be6a2f38752025930e6dbca80d3e0092bbfb905c731fbff2f275e1658176a72`），理由按权重排：

1. **验证集上更好**：最终 6.0325 对 6.0923，且是唯一一条单调下降到底的曲线；宽版最好的验证点在第 2 epoch（6.0847），仍不如窄版的第 3 epoch。后续的行为测量（动作一致率）是在这个分布外样本上量，验证 loss 是这里唯一有的代理。
2. **没有拐头**：宽版已经出现验证回升，等于多花的显存、时间和 24 MB 适配器换来了记忆；拿它做基准会把「记住了训练集」误读成「学会了法」。
3. 次要：42 MB 对 65 MB，重跑 828 秒对 1312 秒，后续每次重生成都省。

代价是把一个未验证的可能性留在桌上：线性注意力的五个投影仍然没有被训练过。这条要作为后续测量的已知边界写下来，不能当成「已排除」。要排除它，得在更大或更多样的数据上再比一次，或者把宽版单独当冷门基线跑行为测量——这两件都不在本次工作包的范围内。

## 复现

```
# 窄版（已有）：6 全注意力层 + MLP
python3 scripts/train_sft.py --epochs 3 --grad-accum 8 --lora-r 16 --lora-alpha 32 \
  --adapter-dir .tmp/sft/adapter-narrow          # 828.6 秒，写 evidence/sft/log.jsonl

# 宽版：再加 18 个线性注意力层的 5 个投影
python3 scripts/train_sft.py --epochs 3 --grad-accum 16 --micro-batch 1 \
  --lora-r 16 --lora-alpha 32 --run-name wide \
  --adapter-dir .tmp/sft/adapter-wide            # 1312.2 秒，写 evidence/sft/log-wide.jsonl
```

`--lora-r` / `--lora-alpha` 是为这次对比新加的：不写就仍按开跑前的空闲显存选 rank，那样两次跑会在 rank 上分叉，比较就不成立。`--run-name` 让两次跑的日志与 summary 不互相覆盖（`log.jsonl` / `log-wide.jsonl`）。窄版的适配器目录已从 `.tmp/sft/adapter/` 改名为 `.tmp/sft/adapter-narrow/`，两个都在 `artifacts.tsv` 里登记。

## 已知边界

- 只对 target 算 loss 的断言两版都保留并通过（`mask_check`：prompt 656 token，第一个有效 label 在 656，得分 159 个 target token，两版逐字段相同）：改动没有碰到掩码路径。
- 数据、截断、max_length 1088、warmup 5 步、优化器 paged_adamw_8bit 两版相同（训练集 8/288 行被截、共 515 个 token，两版相同）。
- 验证集只有 78 条、12 个会话，0.06 PPL 在方法层面是个小差；结论「扩宽没换来泛化」的强度取决于这一点，所以用逐 epoch 的差距趋势与拐头作为主证据，单点 PPL 差只作辅证。
- 三个环境告警与窄版相同：`flash-linear-attention`、`causal_conv1d` 未安装走参考实现，`use_cache` 与梯度检查点冲突被关掉。只影响速度。
- 两版的峰值显存都是在另一个项目同时占卡的条件下测的（窄版开跑时 13.5 GiB 空闲、宽版 7.3 GiB），不能直接当独占显卡的数字。
